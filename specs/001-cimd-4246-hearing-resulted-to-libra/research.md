| R19 (analysis U1) | An attempt left at `SENDING` for longer than `cp.hearing-result.stale-sending-threshold` (default `PT5M`, well above the ≤ 60s call budget) is **stale**. On redelivery, or through a scheduled sweep (every `stale-sending-sweep-interval`, default `PT1M`; worst case to a final outcome = threshold + interval, about 6 min), it is set to `FAILED` with `error_detail = "INTERRUPTED – outcome at GOB unknown"`. **It is never resent automatically.** `alreadySubmitted` skips final statuses and fresh `SENDING` rows. *(Clarified 2026-09-27; still OPEN with BA/GOB, see open item 10.)* | GOB may already have applied the update. Resending without knowing GOB's duplicate behaviour risks a double update on a live account. Making the attempt visible satisfies FR-013/SC-004. | Automatic resend (duplicate risk); leaving it stuck at `SENDING` (silent loss) |
| R20 (analysis C1) | **Timeout budget: each hop's total (connect + read) must be less than its caller's read timeout.** APIM `forward-request` → Libra **35s**. Gateway → APIM connect **5s** / read **40s** (`cp.libra.*`). Workflow → gateway connect **5s** / read **50s** (`cp.enforcement-gateway.*`), total 55s < SC-006's 60s. Workflow → reference data connect **5s** / read **10s** (`cp.reference-data.*`, a separate call before the gateway call). A downstream timeout comes back as a status (APIM 504 → gateway 502 → workflow `FAILED` with `http_status`). A **workflow-side** timeout → `FAILED`, `error_detail = "TIMEOUT – outcome at GOB unknown"`, no resend (same rule as R19). *(Clarified 2026-09-27.)* | The caller outlives the callee, so the real outcome is almost always reported back. The workflow-side timeout is kept only as a last-resort guard. | One shared timeout for all clients; the workflow waiting less than the gateway (outcomes lost) |
| R21 (analysis S1) | Gateway `POST /hearingResulted` access control (FR-018). **Iteration 1: network isolation.** The gateway gets no ingress or external route for this path, and a Kubernetes `NetworkPolicy` admits traffic only from the workflow pod, both in deploy config. **Later iteration: service-to-service bearer auth**, reusing PCR's Entra pattern (`service-cp-crime-results-pcr`: `auth/EntraTokenValidator`, `AuthorizationPolicy`, `EntraAuthProperties`, `AuthMode`, `docs/Authentication.md`, ADR `006-AMP-890-pcr-bearer-auth-security-model.md`). The workflow gets a token for its managed identity; the gateway validates the audience and allowed caller. *(Clarified 2026-09-27; bearer step pending tech lead confirmation.)* | Protects live GOB account updates now, at no code cost, and lines up with an existing sibling precedent | No control (rejected: the endpoint changes live accounts); bearer auth in iteration 1 (delays the MVP; the tech lead hasn't decided yet) |
| R22 (implementation, 2026-09-27; corrected 2026-09-28) | **Outbound payloads are serialised with a NON_NULL JSON mapper** (`PayloadJson` in W, `LibraClient.JSON` in G), and the gateway's HTTP responses use `spring.jackson.default-property-inclusion: non_null`. **Enum-typed properties in the gateway contract have no `maxLength`** (a local amendment in `api-cp-crime-results-enforcementgateway`, commented inline and guarded by an `OpenApiObjectsTest` regression test that scans every generated model). | The Libra schemas are `additionalProperties: false` and not nullable. *Correction (2026-09-28 code review):* the generated models already put `@JsonInclude(NON_NULL)` on optional fields, so the request mappers are a safety net. The response side was the real gap: an empty `{}` Libra reply was passed back with `"caseUrn": null` etc. until the gateway's response serialisation became NON_NULL. The generator turns an enum's `maxLength` into `@Size`, which Hibernate Validator can't apply to an enum (HV000030), so every request failed with a 500. | Configuring the generator per field (not supported); a custom `@Size` validator for enums (hides the contract issue) |
| R23 (implementation, 2026-09-27; corrected 2026-09-28) | `HearingResultedEventListener` uses its own listener container factory (`HearingResultedJmsConfig`), with JMS client id `cp.messaging.hearing-resulted-client-id` on the plain (not caching) connection factory. | Each listener container opens its own connection, and the broker allows one per client id. Found during the T078 end-to-end run: with the shared `spring.jms.client-id`, the new listener never connected. The durable subscription = this client id + `cp.messaging.hearing-resulted-subscription-name`. **This works for a single replica only** (open item 13). | Removing the diagnostics listener (not ours to remove). *Correction:* a JMS 2.0 **shared** durable subscription (`subscriptionShared`) does not need a client id, and is the likely route to multiple replicas; it was not chosen yet (open item 13) |
| R24 (code review, 2026-09-28) | Failure handling tightened after the code review. **Reference data failing** (5xx, timeout, unreachable; 404 still means "no such definition") → `FAILED` with `error_detail` "NOT_SENT – reference data unavailable (…)", with no request and no POST. A 404 is not cached. **Gateway unreachable** (connection refused, connect timeout, unknown host) → `FAILED` "NOT_SENT – enforcement gateway unreachable" (nothing sent). Any other unexpected client error → "ERROR – outcome at GOB unknown". **A 2xx the workflow can't parse** is still `SUCCEEDED`, with the raw reply stored. **Libra 2xx with an empty or invalid body, or any non-2xx including 3xx** → the gateway returns 502, `errorCode` `INVALID_RESPONSE` / `libraStatus` 200, never 500. **`error_detail` keeps codes only** (`error`, `libraStatus`, `errorCode`); Libra's free-text `errorDescription` is not stored (PII risk). **Mapping** now also fails, before any POST, for a missing `hearingDay` (`DATE_OF_HEARING_MISSING`) or a missing / longer-than-7 `courtCentre.code` (`COURT_HEARING_LOCATION_INVALID`), per CIMD-4247 AC3. Telephone numbers longer than 35 are left out, not truncated. An integrity violation other than the unique key is an error, not a duplicate. A case with zero defendants → `NO_DEFENDANT`. | Every attempt ends with a truthful outcome (FR-013). "Not sent" and "outcome unknown" are distinguished for support. No PII outside the payload columns. | Letting these failures escape (the row is lost or stuck at SENDING, or a 500 is returned after GOB applied the update) |
| R25 (integration tests, 2026-09-29) | **Integration test suite that later stories extend with data, not code.** (a) **JMS end to end**: an embedded Artemis broker (`spring.artemis.mode=embedded`) with the `docker` profile, so the real listeners, container factories and client ids run, and each flow is driven by a message on `public.event`, not a direct `process()` call. (b) **Scenario runner**: one folder per scenario under `src/test/resources/scenarios/`, each with a `scenario.json` (event fixture, reference-data answers per result type id, the gateway reply, and the expected POST count and row), and optionally an `expected-request.json`. (c) **Both contracts checked**: every request WireMock receives is validated against the gateway contract (`openapi/openapi-spec.yml` in the API jar W depends on) and the Libra contract, and every stubbed 2xx reply against the gateway `HearingResultedResponse`. `ReferenceDataClient.clearCache()` is added so each scenario starts with an empty shortCode cache; it is also the hook T081's scheduled refresh uses. | The existing tests call `HearingResultedProcessor.process()` directly, so the listener, selector, client ids and JSON parsing were only proven manually (T078), which is how R23 was found late. The HMCTS rule requires an integration test per message-driven entry point. Data-driven scenarios let US5/US6 and contract v0.5.0 add coverage without new test code. | Testcontainers Artemis: needs Docker in every test run and differs from the PCR real-Postgres pattern only by adding weight. Mocking `JmsTemplate`: does not exercise the broker, selector or client ids. One test method per scenario: grows linearly with every story. |
| R24a (integration tests, 2026-09-29) | **A 2xx reply that isn't JSON is stored as a JSON string** in `response_payload` (jsonb), and a blank one as null (`SubmissionStore.recordSucceeded`). | Found by scenario 12 (T094): the raw text was written to the jsonb column, Postgres rejected it, and the row stayed `SENDING` until the sweeper marked it `FAILED – INTERRUPTED` although GOB had accepted it, which contradicts R24. The unit tests used mocks, so only a real database showed it. | Storing null (loses what GOB sent); changing the column to text (loses jsonb querying for every other reply). |
| R26 (gateway integration tests, 2026-09-29) | **The R25 approach, applied to the gateway for both of its flows** (T096-T099): an embedded Artemis broker with the real listeners, one WireMock for APIM and Progression, and scenario folders for `hearing-confirmed` and `hearing-resulted`. It found and fixed two defects. (1) **Open item 11 reproduced**: `HearingAllocationEventListener` shared `spring.jms.client-id` with `PublicEventLoggingListener`, failed with `InvalidClientIDException` and retried forever, so the confirmedHearing flow received no events. It now has its own container factory and client id (`HearingAllocationJmsConfig`, `cp.messaging.hearing-allocation-client-id`), the same fix as R23. (2) **A 2xx reply lacking `caseUrn`, `timestamp` or `nowsDataItems`** was returned as a 200 that broke the gateway contract; it is now `502 INVALID_RESPONSE` with `libraStatus` 200, as R24 intended. The test WireMock has plain-http HTTP/2 disabled: the JDK client's h2c upgrade made WireMock reset the second POST on a connection, which real APIM (HTTP/2 over TLS) doesn't do. | The confirmedHearing flow had no integration test, so the listener clash stayed hypothetical until a broker was involved. | Testcontainers Artemis (Docker in every run). Leaving open item 11 to the tech lead: the flow cannot work at all while it stands. |
| R27 (code review, 2026-09-29) | Review of W, G and A, each fix test-first. **W:** a 3xx from the gateway is `FAILED` "ERROR – outcome at GOB unknown: HTTP 3xx", not SUCCEEDED; the JDBC driver no longer puts Postgres's error detail ("Failing row contains (…)", `request_payload` included) into messages and logs (`logServerErrorDetail: false`); `isReshare` is a `Boolean`, and a missing flag is skipped (`RESHARE_FLAG_MISSING`), never taken as a first share; hearing-level results never match on two missing ids; an event without `hearing` is skipped without an NPE; truncation counts code points; the simulator accepts a request without `nowsDataRequest` (the agreed amendment); a non-text JMS message is logged and dropped rather than redelivered; unused `alreadySubmitted`/`existsBy…` removed. **G:** the confirmedHearing flow logs caseUrn/case id and HTTP status or exception class only, never error bodies or stack traces (constitution IV); a 3xx callback is a failure; an enforcement case without a caseURN is skipped; the hearing-resulted reply is read as UTF-8 whatever its content type, and `INVALID_RESPONSE` carries Libra's real 2xx status; a non-text JMS message is logged and dropped. **A:** README and endpoint description cover `hearingResulted` and both amendments; Spectral runs without the two disabled rules and on `team/**`; tests prove `nowsDataRequest` stays optional and that Bean Validation cascades. | Each was reproduced by a failing test before the fix, except documentation. | Not changed, for a decision: see §2 items 20-24. |
| R18 | The correlation id is **not** sent in iteration 1, because the gateway contract has no `X-Correlation-ID` (smaller item d). Persist the returned `correlationId`. | Keep parity with confirmedHearing | Adding a header now (later iteration) |
