### `hearing_result_submission` and `gob_sent_offence` (features 001, 002) — unchanged schema

**Implementation decision (2026-10-20, replaces the planned V1.010–V1.013):** the notification id is written to the
existing `correlation_id` column of both tables (it held the share correlation id of feature 002). The existing unique
key `uq_hrs_correlation_case_defendant (correlation_id, case_id, defendant_id)` therefore gives exactly "one
submission per notification, case and defendant" (R9), and `gob_sent_offence`'s case/offence keys still give "each
offence once". No migration is needed and applied rows are untouched. `nows_handover_*` columns are no longer written
(the publish outcome lives on the notification). `ShareCorrelationId` is no longer used to build keys.

### Notification state machine (R16)

```text
RECEIVED ──stage 1──► PROCESSING ──► SUBMITTED ─────────────┐   (GOB accepted, new submission)
                                 ├─► SKIPPED_NOTHING_NEW ───┤   (reuse earlier GOB data, FR-009; also every reshare with earlier GOB data)
                                 ├─► SKIPPED_NO_RESULT_CODE   (final; nothing published, FR-010)
                                 ├─► SKIPPED_NOT_ENFORCEMENT  (final; selector skip reasons of 001 FR-004)
                                 ├─► NO_GOB_DATA              (final; FR-009 with no earlier GOB data, incl. a reshare; NOWS stay held)
                                 ├─► GOB_FAILED               (final; rejected / failed / interrupted; manual replay only, R11)
                                 └─► STORED_FAILURE (failed_stage=PROCESS)
                                     (also a reshare without GOB data while a first share of the hearing is in progress:
                                      last_error = FIRST_SHARE_IN_PROGRESS)
                                                            ▼
                                        stage 2 ──► PUBLISHED (final)
                                                ├─► PUBLISH_REJECTED (final; GOB accepted but nothing publishable:
                                                │    no account number, or no notification NOW for the selected
                                                │    defendant's master id; NOWS stay held, reason in last_error)
                                                └─► STORED_FAILURE (failed_stage=PUBLISH)
STORED_FAILURE ──replay (automatic schedule or support)──► resumes the failed stage
```

Validation: `hearingId` UUID; `hearingDate` ISO date; `isReshare` boolean (required); `nows` 1..50 items, each `requestId` and `masterDefendantId`
UUIDs, `requestId` unique within the body.

## H (hearing NOWS service, viewstore PostgreSQL, Liquibase)

### `now_document_request` (existing)

- Enforcement NOWs carry FA's `request_id` and are held in the existing `WAITING_FOR_GOB` status (F4).
- New transition: `WAITING_FOR_GOB` → `ENFORCEMENT_DATA_ADDED` (on the W event, conditional update) → existing chain.
- Feature 002's `master_defendant_id` / `enforcement_correlation_id` columns are no longer mapped or written (R14,
  R26); the columns stay (005 not edited). Status `WAITING_FOR_ENFORCEMENT_DATA` is removed.

### `enforcement_nows_data` (feature 002, changed) — changeset `006-key-enforcement-nows-data-by-request-id.xml`

- Add `request_id` UUID with a unique index; make `correlation_id`, `hearing_day`, `shared_time`,
  `covered_result_definition_ids` NULLable; drop the `(correlation_id, master_defendant_id)` unique constraint.
- One row per request id: `request_id`, `master_defendant_id`, `hearing_id`, `account_number`, `nows_data_items`,
  `gob_data_reused`, `status` (`KEPT` → `CLAIMED` → `RELEASED`, or `KEPT` → `UNCLAIMED` at `release_at`), `user_id`,
  `received_at`, `claimed_at`, `release_at` (received + configurable retention, FR-013).
- A repeated event for the same request id is a no-op (unique index).

## FA (results-processing app)

No storage. Orchestration input/state carries the enforcement NOWs' `{requestId, masterDefendantId}` list between
`EnforcementCaseNowsVariants`, `ProcessEnforcementCaseNowsVariants` and `NotifyEnforcementWorkflow` (research R25).
